# 要件

本ドキュメントは「何を・なぜ実現するか」（目的・動機・要求水準）を記録する。「どう構築したか」（現在のアーキテクチャ）は[architecture.md](architecture.md)、個々の設計判断の根拠・選択経緯は[docs/adr/](adr/)、具体的な業務シナリオは[use-cases.md](use-cases.md)、各サービスの存在意義・業務ルールは[services.md](services.md)を参照。

## 目的

OAuth 2.0 Token Exchange (RFC 8693) の仕組みを、マイクロサービス化された基幹システムを模したローカル実行可能なサンプルで示す。

想定ユースケース: 基幹システムにおける**アクセス権の照会・制御**。あるサービスがユーザーの代わりに下流サービスを呼び出す際、元のユーザーの権限とスコープを適切に絞り込みながら伝播させる。受発注システムをモチーフに、ユーザーの委任がFrontendから複数ホップの下流サービスへ伝播していく流れを構築する。具体的な業務シナリオは[use-cases.md](use-cases.md)、実際のサービス構成は[architecture.md](architecture.md) §2を参照。

各ホップの実装言語は意図的に揃えず、Java・Go・Rust・Python・TypeScriptを使い分ける。技術的な優劣を示すためではなく、Token Exchangeがリダイレクトを伴わないバックチャネルの HTTP+JWT 操作であり、言語間の技術的な優劣が無いことを実演するため（実際のサービスと言語の対応は[architecture.md](architecture.md) §2参照）。

## 背景（なぜ Token Exchange が必要か）

Token Exchange 以前に蔓延していたバッドプラクティスとその課題:

| バッドプラクティス | 問題点 |
|---|---|
| ユーザートークンのそのまま転送 | 下流サービスが「誰経由の呼び出しか」を判別できない。スコープが広すぎるまま伝播する |
| サービスアカウントでの一括呼び出し | ユーザーコンテキストが消失。Confused Deputy Problem の温床 |
| 静的な共有シークレット | ローテーション困難、漏洩時の影響範囲が大きい |

RFC 8693 はこれらを解決するため、スコープ絞り込みによる最小権限の伝播を可能にした。本サンプルでは、下流サービスから見て「元ユーザー」の権限で処理していることが`sub`クレームで判別できるToken Exchange（audienceでダウンスコープしつつ`sub`を維持）でこれを実現する。RFC 8693の用語では`actor_token`を渡さないため厳密には**Impersonation**に分類される点に注意（本サンプルでの実装状況・用語の整理は[architecture.md](architecture.md) §6参照）。

## 委任チェーンの事後監査

RFC 8693 Standard Token Exchange V2では、委任チェーンを表現する`act`クレームが発行トークンに残らない（[architecture.md](architecture.md) §6参照）。つまり、あるサービスが受け取ったトークンだけを見ても「本当に正規の委任チェーンを経て発行されたものか」はJWT自体からは判別できない。

そのため、本サンプルは「元ユーザーの権限とスコープを適切に絞り込みながら伝播させる」（目的節）ことを、トークン発行・検証の時点だけでなく、**事後に第三者が検証できる**形でも示す必要がある。具体的には以下を要件とする。

- サービス間の呼び出し経路（どのサービスがどのサービスを何のために呼んだか）を事後に追跡できること
- 実際に受理されたトークンが、正規のToken Exchangeを経て発行されたものか（迂回して取得されたものではないか）を機械的に検証できること
- 上記の検証が、正常系の動作（サービス間呼び出しのレイテンシ等）を妨げない形で実現できること

実現方法（OpenTelemetryによる経路可視化、Keycloakイベントログとの`(jti, audience)`突合、監査ツール`audit/`の実装）は[architecture.md](architecture.md) §7、設計判断の経緯は[ADR 0005](adr/0005-delegation-audit-with-opentelemetry.md)・[ADR 0012](adr/0012-jti-audience-correlation-for-token-exchange-audit.md)、デモ手順と実行結果は[audit-demo.md](audit-demo.md)を参照。

## 業務ロジックのリアリティ水準

「ある程度リアル」な実装とする。ダミーレスポンスではなく、実在感のあるドメインモデルと業務ルールを持たせる。ダミーレスポンスでは「スコープを絞り込んで委任した先で、実際に意味のある権限チェックが行われているか」を示せないため、この要求水準自体が目的（アクセス権の照会・制御を実演すること）に直結する。

各サービスの存在意義・提供機能・保有データ・業務ルールは[services.md](services.md)、具体的な業務シナリオと委任チェーンの流れは[use-cases.md](use-cases.md)に定義する。
